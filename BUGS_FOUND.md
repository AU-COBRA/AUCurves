# Bugs Found During Pairing Verification (2026-04-11 – 2026-04-12)

## Bug 1: M-twist / D-twist make_line basis swap (Task #21)

**Location**: `bn254-safe-rust/generated/bn254_safe_tower.rs`, function `bn254_make_line`

**Symptom**: Bilinearity check fails: `e(2P, Q) ≠ e(P, Q)^2`

**Root cause**: The BN254 pairing uses a **D-twist** of the curve, which requires the
line evaluation to place components as:
```
c0.c0 = (Py, 0)          # the base-field y-coordinate
c1.c0 = -λ·Px            # negated slope times base-field x
c1.c1 = λ·Tx - Ty        # the main evaluation
```
The committed safe-Rust file had the **M-twist** layout instead:
```
c0.c0 = λ·Tx - Ty        # WRONG position
c0.c1 = -λ·Px            # WRONG position
c1.c1 = (Py, 0)          # WRONG position
```

**How it entered**: The safe-Rust file was generated by an unverified OCaml translator
(`bn254_safe_tower.ml`) from the bedrock2 source. The bedrock2 source
(`BN254_Pairing.v`) had the M-twist layout in its `bn254_make_line` body.
The WP proof (`bn254_make_line_ok`) proved the M-twist body correct *against the
M-twist spec* — but the *spec itself* was wrong for a D-twist curve.

**How it was caught**: The Python multilinearity cross-check (`tests/generate_bn254_multilin.py`)
tests `e(kP, Q) == e(P, Q)^k` for k ∈ {2,3,5,7,11} using precomputed kP coordinates.
This test was added specifically to catch this class of bug.

**Fix**: Added `bn254_make_line_corrected` with the D-twist layout to `BN254_Pairing.v`,
proved it correct in `BN254_PairingHelpers.v` (`bn254_make_line_corrected_ok`, Qed),
and switched all callers to use it.

**Verification gap**: The bug lived in the *hand-edited safe Rust*, not in the Coq proofs.
The Coq proofs were correct for the M-twist spec; the D-twist spec was added later
(`MakeLineBridge.v`, `ZModTest.line_form_matters`).

## Bug 2: Missing Frobenius corrections in optimal-ate Miller loop

**Location**: `BN254_Pairing.v`, function `bn254_miller_loop`

**Symptom**: Bare Miller loop output is not bilinear (expected for BN254 without
Vercauteren corrections).

**Root cause**: The optimal ate pairing for BN curves requires two additional line
evaluations after the main `|6u+2|`-bit Miller loop:
- Q1 = π_p(Q): apply p-Frobenius to the twist point
- -Q2 = -π_p²(Q): apply p²-Frobenius and negate

These were missing from the bedrock2 source. The Rust hand-edit added them, but
the bedrock2 source did not have them.

**Fix**: Added `bn254_miller_loop_optimal` and `bn254_pairing_dsd_optimal` to
`BN254_Pairing.v` with the corrections inline. Constants `bn254_load_gamma1`,
`bn254_load_q1_y_const`, `bn254_load_gamma1_p2` supply the Frobenius values.

## Bug 3: OCaml safe-tower extractor drops while/set/store/cond

**Location**: `src/Bedrock/bn254_safe_tower.ml`

**Symptom**: Extracted Miller loop function does nothing (loop body missing),
scalar stores are comments.

**Root cause**: The OCaml safe-tower translator was designed for flat tower functions
(Fp2 mul, Fp6 add, etc.) that don't use `cmd.while`, `cmd.set`, `cmd.store`, or
`cmd.cond` with compound expressions. The catch-all `| _ -> ()` silently dropped
these constructs.

**How it was caught**: The extracted `bn254_miller_loop_optimal` ran but produced
`f = 1` (the init value) because the 64-iteration while loop was entirely skipped.

**Fix**: Added handlers for `Coq_cmd.Coq_while`, `Coq_cmd.Coq_set`, `Coq_cmd.Coq_store`,
and improved `Coq_cmd.Coq_cond` with recursive `expr_to_rust` for compound expressions.
Also fixed Int64 literal handling for the full u64 range.

**Superseded by**: Phase 1 of the formal refinement plan — the Coq-verified `btranslate`
from `ToSafeRustBody.v` handles all these constructs correctly and is proven by
`SafeRustSimulation.safe_cmd_correct`.

## Bug 4: Variable shadowing causes infinite loop

**Location**: `src/Bedrock/bn254_safe_tower.ml`, `cmd.set` handler

**Symptom**: Miller loop runs forever.

**Root cause**: The `cmd.set` handler emitted `let mut i: u64 = i.wrapping_sub(1);`
inside the while loop body. In Rust, `let mut` creates a NEW binding that SHADOWS
the outer `i`. The while condition `while i != 0` checks the OUTER `i` (still 64),
not the inner (63). The loop never terminates.

**Fix**: Track declared variables; use plain assignment (`i = ...`) for variables
already declared, `let mut` only for first occurrence.

**Superseded by**: Phase 1 — the Coq `btranslate` uses `RScalarSet` which correctly
generates assignment semantics.

## Bug 5: Wrong Montgomery 1 constant in Fp2 inversion

**Location**: `src/Bedrock/bn254_safe_tower_verified.ml`, leaf wrapper for `bn254_Fp2_inv`

**Symptom**: All tower operations involving Fp2 inversion produce wrong results.
The Frobenius corrections fail because the chord slope computation uses Fp2 inv.

**Root cause**: The Fermat inversion loop `a^(p-2)` needs an initial accumulator of 1
in Montgomery form. Montgomery 1 = R mod p where R = 2^256. The correct value is:
```
[0xd35d438dc58f0d9d, 0x0a78eb28f5c70b3d, 0x666ea36f7879462c, 0x0e0a77c19a07df2f]
```
The driver hardcoded a different value:
```
[0xac96341c4ffffffb, 0x36fc76959f60cd29, 0x666ea36f7879462e, 0x0e0a77c19a07df2f]
```
This was `from_word(1)` from fiat-crypto's internal test, NOT `R mod p`.

**How it was caught**: Binary search between the passing (hand-edited) and failing
(verified translator) .rs files. Full-file diff revealed the constant mismatch.

**Fix**: Corrected the constant to `R mod p`.

**Remaining TCB risk**: The `bn254_Fp2_inv` and `bn254_Fp2_opp` leaf wrappers are
still hand-written in the OCaml driver. They should be extracted from the Coq
`bn254_opp_prelude` or verified against the fiat-crypto proofs.

## Bug 6: Duplicate function in extraction list

**Location**: `BN254_Pairing.v`, `bn254_all_pairing_funcs`

**Symptom**: Rust compilation error `E0428: the name bn254_Fp2_conjugate is defined
multiple times`.

**Root cause**: `bn254_Fp2_conjugate` was included both in `PairingOps_funcs` (via
`bn254_pairing_ops`) AND explicitly in the `bn254_all_pairing_funcs` list.

**Fix**: Removed the explicit entry; the function is already provided by `PairingOps_funcs`.

## Lessons

1. **The multilinearity cross-check** (`e(kP,Q) = e(P,Q)^k`) is the most effective
   bug-catcher. It caught bugs 1, 2, and 5 — all of which were in unverified layers.

2. **Unverified translators are the weakest link.** Bugs 1, 3, 4, and 5 all lived in
   the OCaml translator or the hand-edited Rust — outside the Coq verification boundary.
   Replacing the translator with the Coq-verified `btranslate` (Phase 1) eliminates
   bugs 3 and 4 structurally.

3. **Hand-written constants are error-prone.** Bug 5 was a copy-paste error in a
   Montgomery constant. The fix: derive ALL constants from the Coq source via extraction,
   never hardcode them.

4. **The verification boundary must be explicit.** The D-twist bug (1) existed because
   the WP proof verified the M-twist spec — which was internally consistent but wrong
   for the curve. The `MakeLineBridge.v` bridging lemma and `ZModTest.line_form_matters`
   theorem now catch this class of error at the Coq level.
